# Drift demo repository

A real Drift history you can walk through in two minutes. The `.drift/`
metadata (SQLite intent store, content-addressed objects, signing key) is
committed here **on purpose** so `drift log` / `drift blame` / `drift context`
work immediately after cloning — this is the only place in the repo where a
`.drift/` store is committed (normal repos keep it local and gitignored).

## Requirements

Node.js >= 24 and git. Clone the parent repository and install once:

```bash
git clone https://github.com/lilcipherx/drift.git && cd drift
npm install
```

## Walk through

The embedded `.git` history of this demo cannot be committed inside a
repository, so a fresh clone regenerates it first (this dogfoods the CLI:
`init` + three `realize` intents, ~2 s):

```bash
bash scripts/seed-demo.sh     # from the repository root — recreates examples/demo-repo
cd examples/demo-repo

# 1. What happened, and in what order?
node ../../packages/drift-cli/dist/cli.js log

# 2. The core question: WHY does refreshToken exist?
node ../../packages/drift-cli/dist/cli.js blame src/auth.ts --function refreshToken
#    → Why / Generated by (AGENT @ Drift Demo, claude-3-5-sonnet) / Intent / Commit + valid signature

# 3. What context should an agent hydrate before editing this file?
node ../../packages/drift-cli/dist/cli.js context src/auth.ts --limit 5

# 4. Is the store healthy? Are the signatures valid?
node ../../packages/drift-cli/dist/cli.js doctor
node ../../packages/drift-cli/dist/cli.js log --json | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const j=JSON.parse(d);console.log(j.intents[0].id)})" | xargs -I{} node ../../packages/drift-cli/dist/cli.js verify-intent {}
```

## How the demo is built

`scripts/seed-demo.sh` dogfoods the CLI itself: `init` → three `realize`
intents (2 agent + 1 human) → `git add -f .drift` → commit. It recreates
`examples/demo-repo/` with **fresh** intent ids and git history every run.

The committed snapshot in this repository (`src/` + `.drift/`) is a static
reference — the live demo is always the regenerated one. To refresh the
snapshot after changing the demo, run the seed script and commit the updated
files from the repository root.

## Notes

- The signing key here is a **throwaway demo key** — never reuse it for a real
  repository.
- `doctor` may report orphaned intents in a fresh clone: the committed
  `.drift/drift.db` references git SHAs that only exist inside the regenerated
  repo. That is expected — `log`/`blame`/`context` read the object store and
  work fine.
